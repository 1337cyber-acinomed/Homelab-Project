## What this project is

Project Polaris is my homelab (3-node Proxmox cluster: AI, homelab, cyberrange). Phase 4 is building a set of AI agents on top of the backup/automation work from Phases 1-3, running via n8n on the AI node, each with its own dedicated container and its own narrowly-scoped credentials — never a shared, broad identity. The end-state vision: a **foreman agent** is the one thing I talk to directly (eventually via Matrix, so I can reach it from anywhere on Tailscale, not just n8n's own editor); the foreman directs a set of **sub-agents**, each owning a specific domain. Sub-agents are proven working on their own, one at a time, before the foreman is ever built — the foreman's whole job is orchestrating things that already work, not being built alongside them.

## Where things stand — the documentation agent is fully built and proven

This was the first sub-agent, and it's now complete for its originally-scoped capabilities:

- **Model**: `gpt-oss:20b`, chosen after real, empirical multi-model testing (raw speed, tool-calling reliability, and a coding-correctness test specifically designed to defeat memorized-pattern-matching) — not assumed from Phase 2's original default. `qwen3:14b` is a proven backup. This testing methodology and its explicit caveat ("best from what was tested, not a closed list") are worth reusing whenever a future agent's model choice comes up.
- **Five tools, each independently proven and then proven through the real agent**: list a repo's root, read a file/directory (with base64 content decoded deterministically — never asking the model to decode it itself, a real fabrication problem caught and fixed), search by filename, search by content (via a real local `grep` against a fresh clone, not an API loop), and propose/rename changes (branch → commit → PR, always — the agent never has push-to-main access, matching this project's oldest standing rule).
- **Full parity across both real repositories** (`homelab-infrastructure` and `Project_Polaris`) — the four read/search tools are genuinely multi-repo (parameterized), the two write-capable actions (propose, rename) are deliberately duplicated per repo with their own separate forced-command SSH identities, since only those two can actually commit anything.
- **A real, live milestone**: the agent's own authored content (a homepage for the MkDocs-rendered ADR collection, from Phase 4b) has been reviewed, approved, and merged — the first genuinely agent-authored change in this whole project, with the 4b webhook confirmed firing and the live site updating.
- **Several genuinely serious bugs found and fixed along the way**, not just typos — a confident fabrication of an entire fictional repository's content (root-caused to base64 being a near-universal LLM weak point, fixed architecturally rather than by prompting); the model's own generated output containing stray whitespace that corrupted a write/rename call and then caused it to misdiagnose an internal error message as a missing tool parameter; and a systemic Forgejo setting (`default_delete_branch_after_merge: false`, present since the project began) that had been leaving merged branches behind indefinitely, now fixed permanently on both repos. All fully written up in the runbook with root causes, not just fixes.

## A standing decision from this session, worth restating precisely

**Matrix (4d/4e) is reassigned to the foreman, not the documentation agent, and this was a deliberate choice, not a shortcut.** Direct, foreman-free access to a sub-agent has real, ongoing value — it's exactly how every bug above was actually found, watching a sub-agent's raw tool traces without a foreman's own reasoning in between. n8n's own chat panel already provides that, permanently, and is being treated as the documentation agent's real, standing debug interface — not a placeholder. Matrix becomes the actual production interface, reserved for the foreman specifically, once the foreman exists. This reasoning should be revisited explicitly for each future sub-agent, not assumed to automatically apply — but for now, it means the documentation agent doesn't have unfinished Matrix work; that work moved to the foreman's own build, later.

## What's next: design and build the coding agent

Confirmed order: **coding agent next, networking agent after that, foreman last** — deliberately in that order, since the coding agent's work is safely reversible (an unmerged PR costs nothing), while the networking agent will eventually touch VLANs, bridges, DNS records, and ACLs with real, potentially live effects. Any genuinely new pattern (and this session found several — model-output corruption, internal-detail leakage, node-naming collisions) is far better discovered on the coding agent's low-stakes ground than on the networking agent's.

**One explicit principle from this session, meant to apply to every future agent, not just the higher-stakes ones**: every agent deserves the same level of deliberate design conversation and safety-model scrutiny as the documentation agent got — not because of how dangerous its job sounds on paper, but because of what it actually ends up owning and touching, which often isn't fully knowable in advance. The documentation agent's own design changed repeatedly in-situ (Wiki.js → MkDocs, a new repo → the existing one, one overloaded tool → several narrow ones, single-write → read/search/write/rename) — none of that was foreseeable at the start, and the coding agent should be expected to evolve the same way, not designed as if everything can be nailed down up front.

## How I'd like to keep working

Same discipline as this whole project, reinforced hard by this specific session:

- **For any build involving more than one account, credential, or multi-step SSH sequence: one instruction at a time.** State the reason briefly, give exactly one action, wait for confirmation, then the next. This was explicitly requested mid-session after earlier steps bundled too much together, and every complex build afterward (the write path, the rename mechanism, the `Project_Polaris` extension) went cleanly once this became the default — it should stay the default for the coding agent's build, not be reintroduced only after a repeat complaint.
- **Confirm, don't assume — especially anything the model itself claims about its own state, output, or reasoning.** This session's real bugs were consistently found by checking raw tool output against independently-verified ground truth (decoding base64 by hand, tracing a script's actual stdout/stderr, checking a real `curl` response) rather than trusting a plausible-sounding summary.
- **Explicitly label which account/host a command needs to run under, every time**, once more than one is in play — a real, named lesson from this session, added to the runbook's own Working Philosophy section specifically because its absence caused real confusion more than once.
- **Rename every new node in a workflow distinctly at creation time** — a new habit adopted this session after a real naming collision, worth carrying into every future workflow from the start rather than fixing after the fact.
- Keep the runbook updated as we go, not just at the end of a session — this project's whole traceability depends on it, and this session's own entries (especially the step 5 architectural reference) are the model for how much detail is worth capturing.
