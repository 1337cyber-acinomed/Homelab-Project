## Confirmed bug, fixed by upgrade: `page-interfaces-neighbor` did not grant API access on cyber-fw01's pre-upgrade firmware (26.7.1)

The "Interfaces: Neighbors" privilege's ACL pattern is version-dependent:

| Version | `page-interfaces-neighbor` API pattern | Matches `NeighborSettingsController`'s real route (`api/interfaces/neighbor_settings/*`)? |
|---|---|---|
| 26.7, 26.7.1, 26.7.2, 26.7.3 | `api/interfaces/neighbor/*` | **No** |
| 26.7.4, 26.7.5, HEAD | `api/interfaces/neighbor_settings/*` | Yes |

This was checked against the actual anchored-regex matcher in `ACL.php::urlMatch()` (`preg_match("@^/{$match}$@", $url)`), not just eyeballed: pattern `api/interfaces/neighbor/*` compiles to `^/api/interfaces/neighbor(/.*)?$`, which does not match `/api/interfaces/neighbor_settings/searchItem` (ran this exact regex in PHP to confirm — no match). `NeighborSettingsController.php` itself is byte-identical across `26.7.1`, HEAD, and `26.7.5` — the controller's route never changed; it was the privilege's URL pattern in the ACL.xml that was wrong on `26.7.1`–`26.7.3`.

Upstream bug, not specific to this account or config: fixed in commit `ac38db7` ("acl: add missing and fix some issues," cherry-picked from `3286bb3c`), which landed between `26.7.3` and `26.7.4`. Same commit also touched Core, DHCRelay, Diagnostics, Hostdiscovery, and Monit ACL.xml files (confirmed none of those touch a privilege this project uses). The same bug class (API pattern silently missing/wrong for a `*SettingsController`) also affected `page-interfaces-gif-edit` and `page-interfaces-gre-edit` on `26.7.1`–`26.7.3` (their API patterns were `ui/...` instead of `api/...` there, also fixed by the same commit), though neither is used by this project.

**Practical effect, confirmed both ways:** on `26.7.1`, granting `page-interfaces-neighbor` to `polaris-networking-readonly` did **not** unlock `GET /api/interfaces/neighbor_settings/searchItem` (or any other `neighbor_settings` endpoint) — would have 403'd despite showing as granted. Post-upgrade on `26.7.5`, this is fixed and live-confirmed: the same call now returns a successful empty result instead.

## Resolved, 2026-10-03: `Status: Interfaces` and `Interfaces: Neighbors` kept, with a tool-wiring constraint

Both privileges bundle a write/apply action under the same wildcard pattern as their reads (no OPNsense-provided split — confirmed across every `ACL.xml` in core, no narrower privilege exists for either path):

- **`page-status-interfaces`** ("Status: Interfaces") → `api/interfaces/overview/*`. Reads: `interfacesInfoAction`/`getInterfaceAction` (live interface status — link state, assigned IP, MTU, media, in/out counters, for every interface; post-upgrade, `link_type`/`link_typev6` returned separately — see pre-upgrade verification above). Bundled write: `reloadInterfaceAction($identifier)`, reloads/restarts a live interface. Pattern confirmed unchanged `26.7.1` through `26.7.5` — fine as originally analyzed, no version dependency.
- **`page-interfaces-neighbor`** ("Interfaces: Neighbors") → `api/interfaces/neighbor_settings/*` from `26.7.4` onward, confirmed live on the now-running `26.7.5`. Reads: list/detail of configured Neighbor Proxy virtual-interface entries (not live ARP/NDP data — that's separately, correctly covered by `page-diagnostics-arptable`/`page-diagnostics-ndptable`). Bundled write: full CRUD (`setItemAction`/`addItemAction`/`delItemAction`/`reconfigureAction`).

**User's decision: keep both.** Reasoning — Part 1's purpose is issue/breach detection, which benefits from maximum read visibility (including Neighbor Proxy config, even though nothing currently uses that OPNsense feature); the write actions are accepted as a residual, understood risk rather than removed, consistent with how `page-filter-api`'s bundled write capability was already accepted for the drift-checker. Same mitigation applies here and **has been followed in both built tool nodes**: each n8n tool node wired to the AI Agent hits one hardcoded, read-only URL (`interfaces_info`/`get_interface` for status; `search_item`/`get` item for neighbor-proxy) — never a tool node that exposes `reload_interface` or any neighbor-proxy write action as something the AI Agent can call or parameterize. The AI Agent can only invoke the specific tool nodes wired to it, so as long as no tool node ever targets the write actions, those actions stay inert for this credential even though the API key is technically capable of them — the same reasoning that makes `page-filter-api` safe on the drift-checker (fixed code that never calls the write path).

## Standing practice going forward, and the pfSense carryover

**For any future OPNsense privilege/ACL work on this project: always check the actual deployed firmware version's tag, not HEAD/`master`.** This is now proven, not theoretical — a privilege in this very tool list was silently broken for three patch releases and only fixed two releases before the device's version, with no changelog note flagging it as ACL-relevant. HEAD tells you what a privilege *will* do once upgraded, not what it does *now*. Confirmed clean habit going forward: identify the device's version first, `git fetch --depth 1 origin tag <version>`, verify against that exact tag, and re-verify after any firmware upgrade rather than assuming a prior analysis still holds. This round trip (pre-upgrade verification → real upgrade → post-upgrade live confirmation) is the first full end-to-end proof of that practice on this project, and it worked cleanly: nothing was missed, nothing broke that wasn't already flagged.

**Carries over to gateway01 and firewall01 (the two pfSense boxes) before Part 1-equivalent tooling is built for them.** Same discipline, flagged here as a reminder for whenever that work starts: confirm each box's actual installed pfSense version first and verify privilege/API behavior against that version specifically — don't assume an analysis done against pfSense's current docs or GitHub `master` branch matches what's actually running. pfSense uses its own separate privilege-definition system (XML-based privilege descriptions in the pfSense source tree, not OPNsense's ACL.xml/`ACL.php` mechanism), so the exact mechanics here (the `urlMatch()` anchored-regex check, the specific bug/commit) don't carry over directly and will need their own from-scratch source read when that work starts — but the lesson does: **check gateway01's and firewall01's actual running versions, and verify any planned privilege/API mapping against pfSense's source at those exact versions, before building read-only tooling against either one.** Worth doing that version check (and upgrading first, if either is behind) as a standing precondition before scoping that work, the same way the upgrade happened for cyber-fw01 before Part 1 — now demonstrated end-to-end on this device, so it's a proven pattern to repeat, not just a plan.

## Method (for future reference, so this doesn't need re-deriving by screenshot-guessing next time)

1. `git clone --depth 1 https://github.com/opnsense/core` (public repo, read-only, anonymous — no credentials needed).
2. **Check the device's actual firmware version first** (`System → Firmware → Status`, or the version string in the footer) and fetch that exact tag — `git fetch --depth 1 origin tag <version>` — rather than relying on HEAD/`master`. ACL.xml patterns are not stable across releases, even patch releases within the same `X.Y` line: this project found a privilege (`page-interfaces-neighbor`) whose API pattern was flat-out broken for three patch releases (`26.7.1`–`26.7.3`) and silently fixed in `26.7.4`, with no changelog entry calling it out as ACL-relevant. Treat HEAD as "what a privilege will do once the device is upgraded," not "what it does now." After an upgrade, re-fetch the new tag and re-verify — don't assume a prior tag's analysis still applies.
3. Privilege → URL mapping lives in `src/opnsense/mvc/app/models/OPNsense/*/ACL/ACL.xml`, one `<page-xxx>` block per privilege, each with one or more `<pattern>` glob entries (`ui/...` and `api/...`).
4. `grep -rn "<endpoint path>" --include=ACL.xml` finds the owning privilege directly — far faster and more reliable than enumerating the live Privileges GUI by screenshot.
5. To confirm an action actually exists and get its real parameter signature, check the matching `Api/<Controller>Controller.php`'s `*Action()` methods directly, rather than guessing endpoint names from the UI.
6. **To check whether a privilege's pattern actually matches a given URL, don't eyeball the glob — run it through the real matcher.** `ACL.php::urlMatch()` turns the pattern into an anchored regex: `str_replace(['.', '*', '?'], ['\.', '.*', '\?'], $pattern)`, then `preg_match("@^/{$match}$@", $url)`. A pattern like `api/interfaces/neighbor/*` looks close enough to `api/interfaces/neighbor_settings/*` to pass a casual read, but the anchored regex makes clear it isn't — `neighbor` followed by `/.*` requires a literal `/` right after "neighbor," which `neighbor_settings` doesn't have. When in doubt, paste both into a one-line PHP snippet (`preg_match("@^/" . str_replace(['*'],['.*'],$pattern) . "\$@", $url)`) rather than trusting visual similarity.
7. **Before granting any "view"-sounding privilege to a read-only credential, check whether its ACL pattern is a wildcard (`/*`) covering a whole controller** — that's the tell for a bundled read+write grant (no split). Confirmed recurring pattern in OPNsense core, not a one-off: `page-system-advanced-network` (Interfaces Settings), `page-status-interfaces` (Status: Interfaces), and `page-interfaces-neighbor` (Interfaces: Neighbors) all do this, alongside the already-known `page-filter-api`/Kea DHCP cases. **Treat every wildcard-pattern privilege as write-capable until its controller is actually read**, not just the ones that look settings-related by name — `page-status-interfaces` looked like a pure status page and wasn't.
8. When a privilege is kept anyway because its read value is worth the bundled write risk, the mitigation is in the n8n tool wiring, not the OPNsense ACL: build one tool node per hardcoded, read-only URL, and never build a tool node that targets or parameterizes the write action. This is now standing practice for this credential (`page-status-interfaces`, `page-interfaces-neighbor`) and already-established practice for the drift-checker's `page-filter-api`. Both tool nodes for this credential are now built this way, live-confirmed.
9. **When a device gets upgraded, diff the old and new tags across every ACL.xml and every controller file the project's tool list touches — not just the privilege already known to be a problem.** That's the only way to actually confirm "nothing else breaks" rather than assume it. Pattern used here: `git diff <old-tag> <new-tag> -- '**/ACL/ACL.xml'` for the full-tree sweep, then individually diff each controller file in the tool list. Catches both ACL-pattern changes and quieter response-shape changes in the controllers themselves (e.g. `OverviewController`'s `link_typev6` field, added between `26.7.1` and `26.7.5` — harmless here, but the kind of thing worth knowing about before it surprises a tool node's output parsing). Then, after the real upgrade, live-retest the specific thing that was broken plus one or two known-good endpoints as a regression spot-check — this project did exactly that on 2026-10-04 and it caught nothing further wrong, confirming the source-only diff was sufficient on its own.
