## Approval Command Architecture (decided 2026-10-07 — replaces all prior prompt-level approval gating)

**The principle, confirmed directly by the user:** everything except the final commit stays exactly as it is today — the Foreman and Networking Manager still propose, restate, look up, list, and discuss changes conversationally, with no new friction. Only the actual "make this live" trigger moves out of any AI reasoning path entirely, and must come from a direct, deterministic action the user takes in Matrix — because this is a remotely-operated homelab and remote control via Element is a core design requirement, not something to trade away. Rejection does not need this same treatment (explicitly confirmed) — a wrongly-inferred rejection costs nothing but a re-proposal, so it stays conversational via the existing Networking Manager rule (explicit ID required, no guessing).

**The command:** `/approve <id>` (e.g. `/approve 17`), typed directly in the Matrix room. Regex: `^\/approve\s+#?(\d+)$`, case-insensitive, tolerant of an optional `#` and surrounding whitespace.

**Where it intercepts, in the Foreman's n8n workflow:**

1. **Webhook** (existing Matrix intake) — unchanged. In the live workflow, an existing **If** node sits right after the Webhook, filtering to `m.room.message` events not sent by the bot itself — unaffected by this change, still upstream of the new branch.
2. **New Code node — "Detect Approve Command"**, placed immediately after that filtering If node, before Simple Memory or the AI Agent node — **built and tested 2026-10-07**:
```javascript
const message = ($json.body.events[0].content.body || '').trim();
const match = message.match(/^\/approve\s+#?(\d+)$/i);

return [{
  json: {
    ...$json,
    isApproveCommand: !!match,
    pendingId: match ? parseInt(match[1], 10) : null
  }
}];
```
(Note the `...$json` spread — see "Bug found during Step 1" above for why this is required, not optional.)
3. **New If node ("If1")** on `{{$json.isApproveCommand}}` is true — **built and tested 2026-10-07**:
   - **false** → falls through to the existing path, completely unchanged (Simple Memory → AI Agent → everything works exactly as today, including propose/lookup/list/reject). Confirmed via six real Matrix-chat test messages.
   - **true** → enters the deterministic branch below. **The AI Agent node is never reached for this message — this is the entire point.** Confirmed: `/approve 17`, `/approve #17`, `/APPROVE 17` all correctly isolated with `pendingId: 17`.

**The deterministic branch (no AI Agent node anywhere in this path) — built and tested, 2026-10-07 (Step 3):**

4. **Call Lookup directly** — a plain Execute Workflow node pointing at the existing Lookup sub-workflow (not the AI-facing tool wrapper), with `pending_id = {{$json.pendingId}}`.
5. **If `status !== 'pending'`** → build a plain templated reply, no LLM involved: `"Pending change #{{id}} is no longer pending — current status: {{status}}."` or `"No pending change #{{id}} found."` → skip to step 8.
6. **If `status === 'pending'`** → Switch on the looked-up `device` (today: firewall01 only; add a branch the same way when gateway01's write path comes online) → call that device's **dedicated deterministic apply workflow** (`Firewall01 Network Change Apply (Deterministic)` — a separate workflow from the AI-facing Review tool's, see the fix below) **directly**, with `{pending_id, decision: "approve"}` **hardcoded** by this deterministic branch — never passed through from anything AI-generated. **Important correction found during Step 3 testing:** this must NOT point at the same workflow the AI-facing `review_pending_change` tool uses — that workflow carries the Step 2 guard, which correctly blocks anything that isn't `decision: "reject"`, including this trusted caller. See "a third real bug" below for the fix.
7. **Format the confirmation** from Review's output: `"✅ Pending change #{{id}} approved and applied — {{summary}}"` on success, or the honest failure text (e.g. a drift-abort message) if `ok: false`.
8. **Send the reply to Matrix** using the exact same HTTP Request node/credential the Foreman already uses to post its own AI-generated replies — same `polaris-foreman` identity, same room. To the user this reads as one continuous conversation; the only difference is this one reply is templated, not LLM-composed.

**Structural hardening on the AI-facing Review tool (closes the loophole by construction, not by instruction) — built and tested 2026-10-07 (Step 2):** the `review_pending_change` tool wired into the Networking Manager has a hard guard ("Guard — Reject Only") right after its own (AI-facing) entry point: if `decision !== "reject"`, it short-circuits immediately to an error output (`"Approval cannot be issued through this path — it requires the /approve command in chat."`) instead of continuing into the real apply logic (PatchAlias/ApplyChanges/etc.). Confirmed via four direct test-panel cases (`"approve"`, `"Approve"`, `""`, `"reject"`) — only the exact literal `"reject"` passes through. **This makes it structurally impossible for the AI path to reach a live apply, regardless of what the model is told or decides to send** — the same category of fix already used for the `network-manager` credential's scoped privileges (a hard boundary, not a request). The deterministic branch below calls the same underlying apply logic through its own separate, non-AI-facing path, which is allowed to set `decision: "approve"` — **not yet built (Step 3)**.

**System Message changes required (simplifies rather than complicates — the AI no longer needs to reason about approval at all) — applied prior to the Step 3 test round and confirmed live by that testing (Step 4, done):**

**Networking Manager — replace rule 1 entirely:**
> You can never approve a pending change yourself, under any circumstance — that capability has been removed from your tools entirely, and `review_pending_change` will refuse any attempt to approve. If asked to approve or apply a change, tell the user to type `/approve <id>` directly in the chat — that's a separate process you're not part of, and a confirmation will appear once it's done. You may still reject a pending change, but only when the user clearly and specifically names the pending change ID they want rejected — never guess which one.

**Foreman — delete the entire critical-tool approval-gate rule block (both the original 2026-10-06 version and the 2026-10-07 revision), replace with:**
> To apply a pending network change, the user must type `/approve <id>` directly in chat — this is handled by a separate process, not by you, and you cannot trigger it yourself under any circumstance. Once Networking Manager has staged a change and you've restated it, tell the user to use that command when they're ready. You'll never see or need to react to the `/approve` command itself — its confirmation appears in this same conversation automatically. **Endpoint research — pulled live from firewall01's own `/api/v2/documentation` page** (user screenshots, nothing assumed). The Interfaces section of the API is materially more complex than aliases or rules — it is not one endpoint family but **six separate ones**, each with its own associated model and full CRUD:

- **`/api/v2/interface`** (singular) + **`/api/v2/interfaces`** (plural) — associated model `NetworkInterface`. This is the **assignment layer**: it takes a real interface descriptor (`if`, e.g. `igb0` or an already-created VLAN/bridge/LAGG/GRE's own identifier) and turns it into a configured, named pfSense interface (LAN, WAN, OPT1, etc.) with IP/DHCP/MTU/etc. config. **This is the only endpoint family the existing Firewall01 Networking Query Agent currently has wired (`GET /api/v2/interfaces`)** — until the VLAN GET was added this session, see below.
  - `GET /api/v2/interface` — `id` required (query).
  - `POST /api/v2/interface` — creates a new assignment. Required: `if`, `descr`, `typev4` (plus a large number of conditionally-required fields depending on `typev4`/`typev6` — see full field list below). "Applies immediately: No."
  - `PATCH /api/v2/interface` — `id` required; every other field unmarked/optional, same partial-update signal pattern seen on Rules' PATCH — **not yet empirically verified for this endpoint, must confirm before relying on it, per standing "confirm, don't assume" discipline** (Rules' PATCH defied its own "Applies immediately: No" label; cannot assume Interfaces' PATCH behaves the same without testing).
  - `DELETE /api/v2/interface` — `id` required (query), `apply` optional boolean query param, default `false`. "Applies immediately: No." Same shape as the alias DELETE that turned out to have a real presence-vs-value quirk — **must be empirically tested, not assumed, before relying on either value or omission.**
  - Full confirmed field list for POST/PATCH (verbatim from docs): `if` (required), `enable`, `descr` (required), `spoofmac`, `mtu`, `mss`, `media`, `mediaopt`, `blockpriv`, `blockbogons`, `typev4` (required), `ipaddr` (required when `typev4` is `static`/`dhcp`), `subnet` (required when `typev4=static`), `gateway` (when `typev4=static`), `dhcphostname` (when `typev4=dhcp`), `alias_address`/`alias_subnet` (when `typev4=dhcp`), `dhcprejectfrom` (array, when `typev4=dhcp`), `adv_dhcp_config_advanced` and a block of `adv_dhcp_pt_*`/`adv_dhcp_*` advanced-DHCP-timing/override fields (all conditional on `typev4=dhcp` plus `adv_dhcp_config_advanced=true`), `typev6`, `ipaddrv6` (required when `typev6` is one of `staticv6`/`dhcp6`/`slaac`/`6rd`/`track6`/`6to4`), `subnetv6` (required when `typev6=staticv6`), `gatewayv6` (when `typev6=staticv6`), `ipv6usev4iface`/`slaacusev4iface` (PPPoE-related booleans), `prefix_6rd`/`gateway_6rd`/`prefix_6rd_v4plen` (all required when `typev6=6rd`), `track6_interface` (required when `typev6=track6`), `track6_prefix_id_hex`.

### VLAN Apply (Deterministic) workflow — built and live-tested, 2026-10-10

Structure (as originally built, before the id-drift fix described below): `When Executed by Another Workflow` (inputs: `pending_id`, `decision`) → `LoadPendingChange` (exact copy of the pattern used for the Rules Apply precedent) → `Change Switch` (routes on `changeType`: create/modify/delete) → three HTTP Request nodes (`Create`=POST, `Modify`=PATCH, `Delete`=DELETE, all against `/api/v2/interface/vlan`, using the `Firewall01 - network-manager` credential) → shared `finalize` Code node. This is structurally simpler than the Alias precedent (no apply/verify chain needed — VLAN writes are one-and-done, confirmed empirically 2026-10-09) and closer to the Rules Apply workflow's shape.

`finalize` node final code:
```javascript
const { DatabaseSync } = require('node:sqlite');

const loaded = $('LoadPendingChange').first().json;
const response = $json;

const action = loaded.changeType.replace('interface_vlan_', '');
const success = response.code === 200 && response.status === 'ok';

const ledgerDb = new DatabaseSync('/opt/networking-agent/network-change-ledger.db');

if (success) {
  ledgerDb.prepare(`UPDATE pending_changes SET status = 'applied', resolved_at = datetime('now') WHERE id = ?`)
    .run(loaded.pendingId);
  ledgerDb.close();

  const historyDb = new DatabaseSync('/opt/networking-agent/network-change-history.db');
  historyDb.prepare(
    `INSERT INTO change_history (device, change_type, target, previous_state, new_state, applied_at, ledger_ref, notes)
     VALUES (?, ?, ?, ?, ?, datetime('now'), ?, ?)`
  ).run(
    loaded.device,
    loaded.changeType,
    loaded.target,
    JSON.stringify(loaded.currentStateSnapshot),
    JSON.stringify(response.data || null),
    loaded.pendingId,
    null
  );
  historyDb.close();

  return [{ json: { ok: true, pendingId: loaded.pendingId, summary: `VLAN "${loaded.target}" on ${loaded.device} (${action})` } }];
}

ledgerDb.prepare(`UPDATE pending_changes SET status = 'failed', resolved_at = datetime('now'), error_message = ? WHERE id = ?`)
  .run(JSON.stringify(response), loaded.pendingId);
ledgerDb.close();

return [{ json: { ok: false, pendingId: loaded.pendingId, summary: `Failed to apply VLAN ${action} for "${loaded.target}" on ${loaded.device}.` } }];
```

**Bug found and fixed (build-time error, 2026-10-10):** the first version of `finalize` opened a single `DatabaseSync` connection to the ledger DB (`/opt/networking-agent/network-change-ledger.db`) and tried to INSERT into `change_history`, which actually lives in a separate database file (`/opt/networking-agent/network-change-history.db`). This produced `Error: no such table: change_history` on the first live test, *after* the real device write (a VLAN create, tracked as pending change #41) had already succeeded on pfSense. Fixed by using two separate `DatabaseSync` connections, as shown in the final code above. Side effect requiring manual cleanup: ledger row #41 was left stuck in `pending` status even though the VLAN was already live on the device. Reconciled via a one-off script (two separate `DatabaseSync` calls: UPDATE `pending_changes` SET status='applied' for id 41, plus an INSERT of a backfilled row into `change_history`), which the user ran directly — confirmed fixed.

### Structural bug found during full regression testing — VLAN `id` is a live array index, not a persistent identifier, 2026-10-10

**This is the most significant technical finding of this session.** While testing a multi-part delete (tags 151 and 153 in one request, staged as separate pending changes 50 and 49 respectively), approving pendingId 49 (tag 153's deletion) failed with a 404: `"Object with ID 1 does not exist"`.

**Root cause:** pfSense's REST API v2 `id` field for VLAN objects (`/api/v2/interface/vlan`) is not a persistent identifier — it is the live array index into `config.xml`'s `vlan` section. Change #49's snapshot, captured at propose-time, correctly recorded `id: 1` for tag 153 at that moment. But pendingId 50 (tag 151's deletion, which was at a lower index) was approved first, and removing that array entry shifted every entry after it down by one — tag 153 moved from index 1 to index 0. This was confirmed directly: pfSense's own edit page showed tag 153 living at `interfaces_vlan_edit.php?id=0` after the first delete went through, while the Apply workflow was still trying to DELETE the now-stale `id=1` from the original snapshot.

This is a structural exposure, not a one-off edge case: **any `id` captured at propose-time is only valid until the next write to that interface's VLAN array** — whether that write comes from this same pipeline, the pfSense UI directly, or anything else. It affects both `modify` and `delete` (both reference a stored id from propose-time); `create` is unaffected (no existing object to resolve).

**Fix — new nodes inserted into the VLAN Apply (Deterministic) workflow**, between the existing `LoadPendingChange` and `Change Switch` nodes:

```
LoadPendingChange → Get current VLANs → Resolve Current VLAN ID → Resolved OK? (IF)
                                                                      true ↓         false ↓
                                                                   Change Switch    finalize
                                                              (Create/Modify/Delete)
                                                                       ↓
                                                                    finalize
```

- **`Get current VLANs`** — HTTP GET `/api/v2/interface/vlans`, `Firewall01 - net-agent-ro` credential (shared across all three actions; runs unconditionally, cheap).
- **`Resolve Current VLAN ID`** — Code node. For `create`, passes through untouched (no snapshot exists for creates — propose-time snapshot is always `null` for that action). For `modify`/`delete`, matches the stable identifying pair `currentStateSnapshot.if` + `currentStateSnapshot.tag` (which never change) against the freshly-fetched live list, and outputs the *current* id. If no match is found at all — meaning the VLAN was deleted or changed out-of-band since propose — it flags a clean resolve failure rather than guessing. Final code:
```javascript
const loaded = $('LoadPendingChange').first().json;
const vlansResp = $json;
const vlans = vlansResp.data || vlansResp || [];

const action = loaded.changeType.replace('interface_vlan_', '');

if (action === 'create') {
  return [{ json: { ...loaded, resolved: true, resolvedId: null } }];
}

const snap = loaded.currentStateSnapshot;
if (!snap) {
  return [{ json: { ...loaded, resolved: false, resolveError: 'No snapshot recorded for this change.' } }];
}

const match = vlans.find(v =>
  String(v.if).toLowerCase() === String(snap.if).toLowerCase() &&
  Number(v.tag) === Number(snap.tag)
);

if (!match) {
  return [{ json: { ...loaded, resolved: false, resolveError: `VLAN tag ${snap.tag} on ${snap.if} no longer found — state may have changed since this was proposed.` } }];
}

return [{ json: { ...loaded, resolved: true, resolvedId: match.id } }];
```
- **`Resolved OK?`** — IF node checking `{{ $json.resolved }}` is true. True branch feeds the existing `Change Switch` (unchanged — still routes by `changeType`). False branch connects directly to `finalize`, bypassing `Change Switch`/the HTTP write entirely — `finalize`'s existing success check (`response.code === 200 && response.status === 'ok'`) naturally treats this non-matching shape as a failure and records it, so no extra formatting node was needed.
- **`Modify` HTTP node** — body updated to merge the resolved id into the *full* staged change payload (not just the bare id alone — an intermediate draft of this fix briefly replaced the entire body with just the resolved id expression, which would have silently dropped all the actual field changes being applied; this was caught and corrected before testing): `{{ Object.assign({}, $('LoadPendingChange').first().json.proposedChange, { id: $('Resolve Current VLAN ID').first().json.resolvedId }) }}`.
- **`Delete` HTTP node** — URL updated to substitute the resolved id directly: `https://192.168.10.1/api/v2/interface/vlan?id={{ $('Resolve Current VLAN ID').first().json.resolvedId }}`. No merge needed here (unlike Modify) because Delete's `proposedChange` was always just `{ id: found.id }` at propose-time — there's no other payload to preserve.

**Reconciliation and retest:** change #49 was left in `failed` status after the original 404. Reset to `pending` via a one-off script (`UPDATE pending_changes SET status = 'pending', resolved_at = NULL, error_message = NULL WHERE id = 49`), then retested through the fixed chain. Trace confirmed: `Get current VLANs` returned the live list showing tag 153 at `id: 0`; `Resolve Current VLAN ID` correctly matched by `if`+`tag` and output `resolvedId: 0` (overriding the stale `id: 1`); `Resolved OK?` took the true branch; `Delete` correctly hit `?id=0`; `finalize` recorded success. Live pfSense VLANs page confirmed empty afterward (both 151 and 153 gone). **PASSED.**

## 7b: Interfaces Write Capability — Assignment Layer (started and `create`/DHCP proven this session)

**Decision:** with the VLAN sub-scope closed, Interfaces resumed on the assignment layer itself (`/api/v2/interface` + `/interfaces`) — the layer that turns a real interface descriptor (a NIC, or a VLAN/bridge/LAGG/GRE construct already created) into a configured, named pfSense interface with IP/DHCP/MTU/etc. Tool architecture followed the Rules/VLAN precedent: a static-reference **`get_interface_field_help`** tool (mirroring `get_rule_field_help`) plus a **`propose_interface_change`** tool (mirroring `propose_vlan_change`/`propose_rule_change`'s shape), both wired onto the Networking Manager, with a new **"Firewall01 Interface Apply (Deterministic)"** workflow following the VLAN Apply precedent (Switch on `changeType`, HTTP branches per action, shared `finalize`). *(The exact field inventory and `get_interface_field_help` dispatch logic are not independently re-verified here against a pasted copy of the Code node — built and confirmed working by the user directly in n8n, the same way several other build steps in this document were applied and reported done rather than re-pasted; see, e.g., the 2026-10-08 Networking Manager System Message scope-line update.)*

**Foreman prompt changes, this session:** a new Rule 6 was added to the Foreman's System Message, together with a "CONFIRMED:"-line reply template and a proactive/reactive fallback governing when the Foreman should consult the Firewall01 Networking Query Agent to resolve/confirm an interface before staging a change with the Networking Manager — the same general category of fix as the Rules ID-resolution paragraph (2026-10-08), generalized here for interfaces. *(Exact wording not pasted back into this session for the record — applied directly by the user in n8n and reported working, consistent with the same "applied and reported done" pattern noted above. Worth pasting the literal text into this document on a future pass for completeness.)*

**Bug 1 — duplicate-key syntax error in `propose_interface_change`'s Code node, found and fixed.** A copy-paste corruption left a duplicated `ipaddr: ipaddr:` key in the `proposedChange` object literal, throwing `Unexpected token ':'` and blocking every `create` call before it ever reached pfSense. Fixed by removing the duplicate key.

**Bug 2 — the DHCP `ipaddr` sentinel, found and fixed.** Fixing Bug 1 only uncovered a second, separate bug, underscoring that a syntax fix doesn't validate the logic underneath it. An initial fix attempt assumed pfSense only needed the `ipaddr` key present, even as an empty string, for a DHCP-typed create. That assumption was wrong: the live API rejected `"ipaddr": ""` outright with `"Field ipaddr cannot be empty."` (captured directly from the outgoing request/response during testing of what became change #65). **Root cause, confirmed empirically rather than left as a documentation-read guess:** pfSense's legacy `config.xml` schema has never left `ipaddr` blank for a DHCP-configured interface — it stores the literal string `"dhcp"` in that field, the same convention `ipaddrv6` already uses for its own sentinels (`"dhcp6"`, `"slaac"`, etc.). The REST API v2 model carries this forward. **Fix — one field, conditional on `typev4`:**
```javascript
ipaddr: typev4 === 'dhcp' ? 'dhcp' : strOrNull(trigger.ipaddr),
```
This leaves the `static` and `none` paths exactly as they were (both already worked before this bug surfaced — only the DHCP path was ever broken) and sends the literal `"dhcp"` sentinel only when `typev4 === 'dhcp'`, which survives the null-stripping pass since it's never `null`. Full corrected `proposedChange` block for the `create` branch:
```javascript
const proposedChange = {
  if: match.if,
  descr: String(trigger.descr).trim(),
  enable: boolVal(trigger.enable),
  typev4: typev4,
  typev6: 'none',
  ipaddr: typev4 === 'dhcp' ? 'dhcp' : strOrNull(trigger.ipaddr),
  subnet: numOrNull(trigger.subnet),
  gateway: strOrNull(trigger.gateway),
  dhcphostname: strOrNull(trigger.dhcphostname),
  spoofmac: strOrNull(trigger.spoofmac),
  mtu: numOrNull(trigger.mtu),
  mss: numOrNull(trigger.mss),
  media: strOrNull(trigger.media),
  mediaopt: strOrNull(trigger.mediaopt),
  blockpriv: boolVal(trigger.blockpriv),
  blockbogons: boolVal(trigger.blockbogons)
};
Object.keys(proposedChange).forEach(k => { if (proposedChange[k] === null) delete proposedChange[k]; });
```

**Confirmed live, change #66:** staged, `/approve 66`, applied with no errors, and independently confirmed by the user in the pfSense GUI (Interfaces → Assignments) — it is live. **The full chain is proven end-to-end through real Matrix conversation, not just standalone node execution:** Firewall01 Networking Query Agent confirms the target interface → a `CONFIRMED:`-line reply → Networking Manager → `propose_interface_change` → ledger → `/approve` → the deterministic Interface Apply workflow → pfSense.

**Interface Apply (Deterministic) workflow** follows the VLAN precedent's shape (`LoadPendingChange` → `Change Switch` on `changeType` → HTTP branch per action → shared `finalize`). **Apply-immediacy for `PATCH`/`DELETE /api/v2/interface` remains unconfirmed in this document** — the docs mark all three methods "Applies immediately: No," and per the standing "confirm, don't assume" discipline (Rules' PATCH defied an identical label; VLANs' held up) this must be tested empirically, the same way every other endpoint family in this build was, before `modify`/`delete` are relied on. `create`'s own apply-immediacy was observed rather than isolated (change #66 landed live with no separate apply step taken) — worth a dedicated before/after confirmation pass alongside the `modify`/`delete` testing below.

**Scope closed so far: `create` with `typev4: dhcp` only.** Three gaps remain open, carried into Open Items below: `modify` and `delete` are unexercised; `create` with `typev4: static` is unexercised; and a real validation gap exists — the Code node does not enforce `ipaddr`/`subnet` as required when `typev4 === 'static'`, so a static create submitted with no IP would currently stage silently rather than reject at propose time.

**Finding B — fabrication bug, characterized and closed, 2026-10-07 (Step 6):** originally, "list pending changes on firewall01" caused the Foreman to falsely claim it has no tool for this and invent a nonexistent workaround ("check the change-tracker in your configuration-management system"), despite a near-identical phrasing working correctly minutes earlier with the exact same underlying tool. This confirms the underlying pattern behind Finding B — the model occasionally misjudging whether a tool exists for a given phrasing — is a general small-model reliability characteristic that can surface on any "do I have a tool for X" judgment, not a bug specific to `list_pending_changes`. Noted as a known characteristic to monitor, not pursued as a dedicated fix.

## Standing Principles (inherited from Phases 3-4, non-negotiable unless explicitly revisited)

- **No reasoning agent ever holds push-to-main, merge, or other destructive credentials — ever, for any tier of change.** **Extended 2026-10-07 to a sharper form: no reasoning agent may hold the *ability to trigger* a destructive action either, even indirectly through its own tool-calling, if that ability can be exercised in a way that diverges from the agent's own stated decision.** This is a strengthening of the credential-isolation principle, not a new one — the credential was always isolated to the Executor; what wasn't isolated was the *trigger path* into that credential's use.
- **A prompt-level rule, however well-tested through repeated conversational trials, cannot provide a hard guarantee against a critical action — only reduce its probability.** New, 2026-10-07, the single most important finding of this build phase: extensive testing of the critical-tool approval rule produced many correct outcomes, which felt like validation, right up until one execution showed the model's tool-calling and its final narration diverging within a single turn. **A hard guarantee requires removing the capability from the AI-controlled path structurally — a prompt can shape behavior, but only an architectural boundary (a credential it doesn't hold, a tool it structurally cannot call with certain parameters, a trigger it never receives) can guarantee it.**
- **A test that produces the correct outcome is not the same as a test that validates the rule.** Extended 2026-10-07: this applies not just to whether a specific rule *condition* was exercised, but to whether the *chat-visible outcome* reflects everything that actually happened. Checking only the final reply is not sufficient to validate a critical-tool safety property — the full execution/tool-call trace must be checked, since a model's final narration can diverge from what it actually executed during reasoning.
- **One credential, one purpose, proven empirically before being trusted.**
- **Sandbox-execution pattern.** Reasoning and real work happen in different places.
- **Confirm, don't assume.** Reinforced repeatedly throughout 7b's build — most recently and most importantly by the user directly cross-referencing n8n execution IDs rather than accepting the chat-visible outcome as sufficient evidence, and by the discipline of pulling live API docs for each new endpoint family rather than assuming behavior carries over from a similar-looking prior endpoint (Rules' PATCH defying its own docs; aliases' DELETE key-presence-vs-value quirk; Interfaces' PATCH/DELETE apply-immediacy explicitly flagged as unverified pending empirical test; VLANs' `id` field turning out to be a live array index rather than a persistent identifier).
- **No tool-backed agent may fabricate specifics.** Confirmed under multiple real failures and non-failures. The Finding B fabrication bug (false "no tool exists" claim) remains open and is a live, current example of this principle's ongoing relevance.
- **A rule that asks a smaller model to make an open-ended judgment call is weaker than a rule that gives it a concrete pattern to match, with explicit negative examples, AND a check on what context that pattern is allowed to apply in.** Still true as far as it goes — but as of 2026-10-07, understood as a way to reduce risk on tools where an architectural boundary isn't available, not a substitute for one where it is.
- **A capability that technically exists in the system is invisible to an agent unless its own System Message tells it the capability is available and when to reach for it.** Still true; 2026-10-07's Finding B shows System Message correctness is necessary but not provably sufficient for reliable invocation across all phrasings.
- **A fact used to gate a critical action must be verified with a fresh tool call at the moment it's needed, never inferred from conversational memory or recency.** Still a valid principle for every remaining AI-driven decision in this system (propose validity, list accuracy, reject targeting) — it just turned out to be insufficient on its own for the one action (approve) that needed a harder guarantee than any fact-check inside the model's own reasoning could provide.
- **A live/current-state question must be answered from a tool call made in the same turn, never from memory of an earlier result — and a multi-part or multi-device question must get a fresh tool call for every part.** 3-device retest still deferred until memory has genuinely lapsed.
- **A Foreman (or sub-agent) System Message that states a capability doesn't exist will be believed and obeyed, even after the capability is actually built — this is not fabrication, it's correctly following stale instructions. The inverse also holds: a tool wired into the workflow canvas but never mentioned in the System Message is effectively invisible, or worse, ungoverned by any rule the System Message would otherwise have supplied.**
- **A device-specific drift-diff comparison must exclude any field a backend updates on its own, independent of real configuration changes.**
- **A "pure design decision" is a means, not a rule for its own sake — revisit it when it conflicts with something else that matters more, as long as the actual underlying goal is preserved.** Applied at the largest scale yet 2026-10-07: the entire critical-tool approval-tiering design, including its refinement, was discarded in favor of a structurally different approach once it conflicted with the actual goal (a hard guarantee) that it existed to serve.
- **The confirmation-gate for a foreman tool is decided tool-by-tool, based on whether the tool's own worst-case action already passes through a human-gated step.** Refined 2026-10-07: for a tool whose worst-case action is live-infrastructure-changing, "a human-gated step" must mean a step the AI cannot itself trigger — not a step the AI is instructed to wait for.
- **A fast, automated caller can expose timing races that a human operator's natural pacing never would.**
- **Before trusting any privilege/ACL/API analysis of a vendor's open-source firmware against a real device, verify it against the source at the device's actual deployed version — not the upstream project's `HEAD`/`master`.**
- **When multiple foreman tools cover overlapping subject matter, write deliberate disambiguating language into both the tool descriptions and the System Message before wiring the new one in.**
- **A capability exposed through a per-device Networking Query Agent is a tool of that sub-workflow's own inner AI Agent, not a Foreman-level tool.**
- **Separation of agent roles is itself a standing design goal, not just an implementation detail.**
- **A `Call n8n Workflow Tool` node's mapped input fields can silently omit a field entirely, not just have its "From AI" toggle left off.**
- **n8n's Workflow Input Schema has no Required/Optional setting — only a field's Name and Type.**
- **A Simple Memory node's "Session ID: Connected Chat Trigger Node" setting only works when the workflow's actual entry point is a chat trigger.**
- **Per-room conversational memory may legitimately carry device identity across a vague follow-up; Simple Memory's Context Window Length stays at n8n's default of 5 turns.** Does not and will not apply to write-action approvals — now moot for approvals specifically, since approval no longer goes through any AI memory path at all.
- **A write action against a list-type API field must never assume merge/append semantics — verify against the real schema first.**
- **A "staged but not yet applied" API semantic must be identified and accounted for before building a write action, and whether an apply call is global or scoped must be confirmed rather than assumed.**
- **A vendor API's own reported "success" field cannot be assumed reliable — verify it against an independent signal before trusting it as a pass/fail gate.**
- **A chat surface's actual UI affordances must be confirmed, not assumed, before designing a disambiguation flow around them.**
- **An n8n Code node's exact conventions (trigger-access pattern, result-shape, naming style) should be copied from an existing sibling tool rather than reinvented, even when the new tool's logic differs.**
- **When a tool field is semantically optional but the runtime behavior of "optional" on a given platform is uncertain, prefer a design that works correctly regardless of how that uncertainty resolves.**
- **An AI Agent node's tool-calling behavior during reasoning and its final synthesized reply are two separate things that can diverge — a safety rule aimed only at the final reply's content does not constrain the tool calls made on the way to it.** New, 2026-10-07, the core technical lesson of this entire session — distinct from, and more fundamental than, the "test validates the rule" principle above, which is about how to *catch* this; this principle is about *why it happens* and *what kind of fix actually closes it* (architectural, not prompted). **Reconfirmed 2026-10-10 in a new flavor: the divergence isn't limited to whether a tool was called at all — a real, successful call can still be narrated incorrectly (the wrong target named), so even a confirmed tool-call trace must be checked against which specific target it actually acted on, not just that some call happened.**
- **A Code node inserted upstream of existing nodes must preserve the original item's fields (spread the input, e.g. `...$json`) unless every downstream expression that depends on those fields is also being rewritten.** New, 2026-10-07, found while building the Detect-Approve-Command branch: the first version of that Code node returned only its own two new fields, which silently broke the AI Agent's and Simple Memory's existing `$json.body...` expressions on the False (unaffected-path) branch — not because that path's logic changed, but because a node upstream of it changed the shape of `$json` without those downstream nodes being touched at all. The general lesson: inserting a new node into an existing data path is not neutral by default — it must explicitly preserve whatever shape downstream consumers already depend on, unless those consumers are being updated in the same change.
- **Pointing a trusted caller at the same guarded entry point used by an untrusted caller doesn't give the trusted caller a bypass — it just makes the guard correctly block the trusted caller too.** New, 2026-10-07, found when the deterministic apply branch's first version called the same "Firewall01 Network Change Review" workflow the AI-facing, guarded `review_pending_change` tool uses, and was duly rejected by the Step 2 guard exactly as designed. A guard that checks a parameter (like `decision`) has no way to know who's calling it — trust has to be expressed structurally, via which entry point/workflow is reachable from where, not by a caller simply being "the good one" and hoping the shared gate recognizes that. The fix was a genuinely separate workflow for the deterministic path (never wired to any AI tool, so never reachable by the AI — that unreachability *is* its security boundary), not a flag or bypass parameter on the shared one.
- **`$('NodeName').item` depends on n8n's internal pairedItem lineage tracking, which is a separate mechanism from the item's actual field values — fixing the data shape (the spread-`$json` fix above) does not fix broken lineage, and vice versa.** New, 2026-10-07, the root cause of a real production bug: the Foreman's existing `AI Response` node (and the new `Matrix Response` node, which copied it) resolved the Matrix room ID via `$('Webhook').item.json.body.events[0].room_id`. This worked for a plain conversational reply with no tool call, but silently resolved to an empty string — producing a malformed URL and a cryptic Matrix-side `M_BAD_JSON`/"leading sigil" error — specifically when the AI Agent called a tool (a sub-workflow) during its reasoning loop before composing its final reply, which is known to break n8n's pairedItem lineage tracking. **The fix, and the rule going forward: prefer `$('NodeName').first().json` over `$('NodeName').item.json` whenever referencing a node that is known to produce exactly one item per execution** (a webhook trigger, a workflow trigger) — `.first()` reads that node's output directly with no dependency on lineage, and this project already had the correct pattern in active use elsewhere (the `ListPending` Code node) before this bug was found, it just hadn't been applied to the Matrix-send nodes. **Diagnosed, not guessed** — multiple wrong hypotheses (message-content/markdown formatting, a test-harness artifact) were ruled out by inspecting the actual outgoing HTTP request body/URL rather than reasoning about it from the error text alone, consistent with the project's standing "confirm, don't assume" principle.
- **A multi-model-family API surface (e.g. pfSense's Interfaces section) may split one conceptual domain into several structurally separate endpoint families, each with its own model and CRUD — never assume one domain maps to one endpoint family just because aliases and rules each did.** New, 2026-10-09, found while researching Interfaces: unlike aliases (one family) and rules (one family), pfSense's Interfaces API is six separate endpoint families (assignment, vlan, bridge, lagg, gre, group), several of which must cooperate in sequence (create a VLAN construct, then separately assign it) to accomplish one user-facing action. Any new domain's endpoint shape must be mapped from the live docs before assuming a single-tool, single-call design will fit.
- **An API's `id` field cannot be assumed to be a persistent identifier — it may be a live array index that shifts on every write to the same collection, and must be re-resolved by a stable identifying attribute immediately before every use, not trusted from a propose-time snapshot.** New, 2026-10-10, the most significant finding of the VLAN build: pfSense's `/api/v2/interface/vlan` `id` is the live index into `config.xml`'s VLAN array, not a durable key. A staged `delete` whose snapshot correctly recorded `id: 1` at propose-time failed with a 404 once an earlier-indexed VLAN was deleted first, shifting every later entry's index down by one. The fix generalizes beyond this one endpoint: any apply-time action that references an id captured earlier must re-fetch the live collection and re-resolve the target by a stable pair of attributes (here, `if` + `tag`, which never change) rather than trusting the stored id, and must fail cleanly (not guess) if no match is found. This is a stronger, structural form of "confirm, don't assume" specifically for object identifiers.
- **A Simple Memory node's session-scoped risk (narrating from a stale remembered answer instead of re-verifying) is a property of any agent that has its own Simple Memory node, not just the one holding the direct user-facing conversation.** New, 2026-10-10, correcting an earlier assumption in this project: this was previously assumed to be Foreman-specific, since the Foreman is the agent in the multi-turn conversation with the user. Live testing showed the Firewall01 Networking Query Agent — a sub-agent, invoked by the Foreman, never directly user-facing — exhibit the identical "repeat my own stale earlier answer instead of re-attempting" pattern. The correct generalization: n8n's Simple Memory is keyed by session, not reset per sub-workflow invocation, so *every* agent in this system that carries its own Simple Memory node needs the same re-verification discipline applied to its own System Message, not just the Foreman's.
- **A field that technically accepts "any non-null value" may still require one specific sentinel value for a given mode, not just a placeholder or empty string — this must be confirmed against the live API, not inferred from "the key must be present."** New, this session, found on `propose_interface_change`'s `ipaddr` field: pfSense's real API rejected an empty string for a DHCP-typed interface create, requiring the literal string `"dhcp"` instead — a legacy `config.xml` convention also used by `ipaddrv6`'s `"dhcp6"`/`"slaac"` sentinels. Consistent with, and an extension of, the project's standing "confirm, don't assume" discipline: a hypothesis about API behavior (even a well-grounded one, as this was) is still a hypothesis until tested against the real endpoint.
